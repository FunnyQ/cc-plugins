## Goal

`cockpit channel` completes the MCP stdio handshake exactly as the Bun channel does, and the spike settles once whether rmcp can carry cockpit's experimental capability and custom notifications or the channel must use hand-rolled JSON-RPC.

## Files to create / modify

- `packages/monitor/cockpit-rs/Cargo.toml` (modify) — add `rmcp` (server + stdio transport features only), pinned to an exact minor version, with a one-line justification comment; and extend the existing `tokio` dependency's features with `rt`, `io-std`, `io-util`, `signal`, `time`, `sync` so the channel compiles on its own (also with the hand-rolled fallback, which gets no features through rmcp).
- `packages/monitor/cockpit-rs/Cargo.lock` (modify) — regenerated by cargo.
- `packages/monitor/cockpit-rs/src/channel/mod.rs` (new) — the `cockpit channel` entry: MCP server setup, capability declaration, `tools/list`, notification send/receive plumbing, stdin-EOF/SIGTERM exit.
- `packages/monitor/cockpit-rs/src/main.rs` (modify) — route the `channel` subcommand to `channel::run()`.

## Implementation notes

### Look the API up first

Before writing any code, query rmcp's current docs:

```bash
bunx ctx7 docs /websites/rs_rmcp_rmcp "ServerCapabilities experimental field and ServerInfo instructions"
bunx ctx7 docs /websites/rs_rmcp_rmcp "send CustomNotification with arbitrary method from a server via Peer"
bunx ctx7 docs /websites/rs_rmcp_rmcp "ServerHandler on_custom_notification receive unknown client notification"
```

Known facts (docs.rs/rmcp): `rmcp::model::CustomNotification { method: String, params: Option<Value>, extensions }` exists, and `ClientNotification` has a `CustomNotification(CustomNotification)` variant. Confirm the server-side counterpart (`ServerNotification::CustomNotification` or equivalent) and the handler hook for inbound custom notifications in the version you pin.

### What the handshake must produce (byte-level parity target)

The Bun channel builds its server like this; reproduce every value:

- `serverInfo`: `{ "name": "cockpit-channel", "version": "0.0.1" }`.
- `instructions` (exact string, including the angle brackets and quotes):
  `Messages from the cockpit dashboard arrive as <channel source="cockpit">...</channel>.`
- `capabilities`: `{ "experimental": { "claude/channel": {}, "claude/channel/permission": {} }, "tools": {} }`. No other capability keys (no `resources`, `prompts`, `logging`). The whole `capabilities` object must equal this exactly; if rmcp cannot emit it without an extra key, that is an rmcp failure and triggers the hand-rolled fallback.
- `tools/list` → `{ "tools": [] }`.
- Echo the client's requested `protocolVersion` the way rmcp/the TS SDK negotiate it; the `channel: handshake` group pins what is expected.

### The three capabilities the spike must prove

1. **Declare** `experimental: {"claude/channel":{}, "claude/channel/permission":{}}` together with `tools: {}`.
2. **Send** arbitrary-method notifications with arbitrary JSON params:
   - `notifications/claude/channel` with `{ "content": "<text>", "meta": { "source": "cockpit" } }`
   - `notifications/claude/channel/permission` with `{ "request_id": "<id>", "behavior": "allow" | "deny" }`
3. **Receive** arbitrary-method client notifications, in particular `notifications/claude/channel/permission_request` (params `{ request_id, tool_name, description, input_preview }`), and dispatch by method name to a Rust callback. An unknown non-permission notification must be ignored without error or disconnect.

Prove (2) and (3) with a `cargo test` that drives the server over an in-memory duplex (or rmcp's test transport): send `initialize` + `notifications/initialized`, emit both outbound notifications and assert the exact JSON lines, feed a `permission_request` and assert the callback got the method and params.

### Decision rule

- All three work with rmcp → keep rmcp. First line of `src/channel/mod.rs`:
  `// MCP transport: rmcp <exact version> (experimental caps + custom notifications verified)`
- Any one fails → drop rmcp from `Cargo.toml`, implement newline-delimited JSON-RPC 2.0 over stdin/stdout with `serde_json` (read one line = one message; respond to `initialize`, `tools/list`, `ping`; accept `notifications/initialized`; unknown request methods → JSON-RPC error `-32601`; dispatch notifications by method). First line of `src/channel/mod.rs`:
  `// MCP transport: hand-rolled JSON-RPC (rmcp <exact version> failed: <which capability, one clause>)`
- Either way, the public surface later work builds on is:

```rust
/// Outbound notification to the Claude session. Serialized by the caller.
pub async fn notify(&self, method: &str, params: serde_json::Value) -> anyhow::Result<()>;
/// Register a handler for inbound client notifications; receives (method, params).
pub fn on_notification(&mut self, f: impl Fn(String, Option<serde_json::Value>) + Send + 'static);
```

Name the wrapper type `ChannelPeer` (or keep rmcp's `Peer` behind these two functions); the rest of the channel must never depend on which transport won.

### Scope of `run()` in this task

- Runtime: `main` stays synchronous (never `#[tokio::main]`). The synchronous `channel::run` builds its own `current_thread` runtime with `tokio::runtime::Builder::new_current_thread().enable_all().build()`; no multi-thread runtime, never a runtime in `main.rs`.
- Start the MCP server on stdio, serve the handshake and `tools/list`, then idle.
- Exit with status 0 on stdin EOF, and on SIGTERM/SIGINT (`tokio::signal::unix`). Claude Code closes the pipe when the session ends; a channel that keeps running gets reparented to PID 1 and polls forever, so exit immediately with nothing to flush.
- No daemon contact yet: no `daemon.json` read, no inbox poll, no server spawn, no session-id resolution.
- Leave `channel.contract.test.ts` untouched. Its `channel: handshake` group waits for an authenticated daemon request, so the Rust binary cannot pass it until the full-channel task adds the inbox loop, and that task runs every `channel: ` group against Rust.

### Idle RSS measurement

After `cargo build --release`, measure the idle channel with stdin held open and record the number:

```bash
BIN=$PWD/packages/monitor/cockpit-rs/target/release/cockpit COCKPIT_HOME=$(mktemp -d) bun -e '
const p = Bun.spawn([process.env.BIN, "channel"], { stdin: "pipe", stdout: "ignore", stderr: "inherit" });
await Bun.sleep(3000);
const ps = Bun.spawn(["ps", "-o", "rss=", "-p", String(p.pid)]);
console.log((await new Response(ps.stdout).text()).trim());
p.kill(); await p.exited;'
```

Hold stdin open with `Bun.spawn` and read the real channel pid from the subprocess. Never use `$!` of a backgrounded pipeline: in bash that is a subshell's pid, so `ps` would measure the shell and `kill` would leave the channel running. The printed number is KB.
