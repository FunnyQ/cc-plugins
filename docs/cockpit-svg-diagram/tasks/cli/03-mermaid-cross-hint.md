## Goal

An SVG whose root element is preceded by junk is diagnosed as an SVG problem, not as an unrecognised Mermaid diagram type.

## Files to create / modify

- `packages/monitor/skills/cockpit/scripts/diagram-lint.ts` (modify) — the first-line rejection gains a cross-format branch.
- `packages/monitor/skills/cockpit/scripts/diagram-lint.test.ts` (modify) — cases for the new branch.

## Implementation notes

### Why this branch exists

Format detection asks one question: is the first non-whitespace character `<`? That rule is reliable in both directions and it is the only detection point in the system. It leaves exactly one gap — an SVG document that does not start at its root element.

That happens in practice. A shell heredoc swallows the `<?xml …?>` prolog. A copy-paste starts mid-file. An export tool writes a banner line above the root. A byte-order mark or a stray leading word survives a trim that only strips whitespace. In every one of those cases the source is routed to the Mermaid lint, which reports:

```
first line "Generated by Excalidraw" is not a Mermaid diagram type — start with e.g. "flowchart TD", "stateDiagram-v2", "sequenceDiagram"
```

The author now believes they wrote bad Mermaid. They did not. They wrote good SVG with a bad first line, and the message points them at the wrong language entirely.

### The alternative that was rejected

A `--diagram-format mermaid|svg` flag would remove the ambiguity by making the author declare their intent. It was rejected during design: it is a second code path to test, a third parameter to document across the authoring references, and an agent composing a diagram will forget to pass it — so the flag would be absent in exactly the confused case it was meant to serve. A message the author reads at the moment they are confused costs one branch and cannot be forgotten. Do not add the flag.

### The exact code being modified

`lintDiagram(src: string): Promise<string[]>` in `packages/monitor/skills/cockpit/scripts/diagram-lint.ts` returns `[]` when clean, otherwise one message per problem, each phrased `what's wrong — how to fix`. It never throws.

Its first check, after the empty-source guard, computes `firstMeaningfulLine(src)` — which skips a leading `---` YAML frontmatter block, blank lines, and `%%` comments — takes that line's first whitespace-delimited word, and tests it against the `DIAGRAM_TYPES` set (35 first-line keywords the vendored mermaid v11 bundle accepts; none begins with `<`). When the word is absent from the set the function **returns immediately** with a single message and runs nothing else:

```ts
const first = firstMeaningfulLine(src);
const typeWord = first?.split(/\s/)[0] ?? "";
if (!first || !DIAGRAM_TYPES.has(typeWord)) {
  // Stop here: mermaid's own "no diagram type detected" adds nothing, and
  // every downstream rule would be linting a language it can't identify.
  return [
    `first line "${first ?? ""}" is not a Mermaid diagram type — start with e.g. "flowchart TD", "stateDiagram-v2", "sequenceDiagram"`,
  ];
}
```

That early return exists so no downstream rule ever lints a language it cannot identify. **The new branch sits inside this block and must preserve that property**: one message, immediate return, no `:::class` scan, no headless parse, no heuristics.

### The new behaviour

Inside that block, before building the message, test whether the source contains an SVG tag opening:

```ts
const LOOKS_LIKE_SVG = /<svg[\s>]/i;
```

Match the tag-open form, not the bare word. `/<svg[\s>]/i` requires a whitespace character or a closing angle bracket after the element name, so the word "svg" appearing in prose or in a node label does not trigger it.

When the pattern matches, return the SVG-flavoured message instead. It must state three things: that the source looks like SVG, that its root element is preceded by something else, and the two ways to fix it. Use this wording:

```ts
`first line "${first ?? ""}" is not a Mermaid diagram type, but the source contains an "<svg" tag — this looks like SVG whose root element is preceded by other content. Delete everything before "<svg", or pass the file directly with --diagram @path.svg`
```

Keep it in the same `what's wrong — how to fix` voice as every other message in the file. It is user-facing text an agent will act on, so the fix half must be executable as written.

When the pattern does not match, return the existing message byte-for-byte unchanged.

### One accepted false positive

A Mermaid source whose first line is already broken **and** which embeds a literal `<svg>` tag inside a node label will receive the SVG hint rather than the diagram-type hint. That source is broken either way, and the author has to fix the first line before anything else can be checked, so a hint aimed at the wrong half of a doubly-broken source costs nothing. Do not add a heuristic to disambiguate it — that would be a rule guarding a case with no real cost.

### What must not change

- No existing message text changes. The typo case must produce the same string it produces today.
- No downstream rule may begin running on the early-return path.
- The lint still never throws, and still degrades silently when happy-dom is unavailable.

## Out of scope

- **Accepting the prefixed SVG anyway** — Deferred. The lint reports; it never rewrites the author's source. Trimming the junk here would make the stored trail differ from what the author passed, which the design explicitly forbids.
- **Any change to the SVG lint itself** — Deferred. This task only touches the Mermaid path's first-line rejection. The SVG validator is a separate file with its own task.
- **Adding a `--diagram-format` flag** — Rejected during design, not deferred. The whole point of this branch is that a message cannot be forgotten while a flag can.
- **Disambiguating a literal `<svg>` inside a Mermaid node label** — Deferred. That source is broken regardless of which hint it gets, so the rule would guard a case with no cost.
